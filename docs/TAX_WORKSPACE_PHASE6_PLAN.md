## 1. 一括確認リスト（設計方針 §9-2 の改訂）

### 1.1 何を変えるか

これまで「一括登録・全件登録のボタンを作らない」を禁止事項にしてきた
（`TAX_WORKSPACE_PLAN.md` §9-2）。中堅レビューの実測で、
**カード1枚が1画面に2枚しか入らず、100件の月では約43画面分のスクロールになる**
ことが確認され、「この一線を緩めない限り件数が多い月は速さでMFに勝てない」
という評価だった。

中堅レビューの代案を採用する:
**「確認の単位」と「実行の単位」を分ける。**

> 見た目は一覧でまとめて確認するが、**実行はこれまでどおり1件ずつ**。
> サーバー側のAPI・安全装置・操作履歴は**一切変えない**。

### 1.2 設計

①未仕訳の明細タブに**表示の切り替え**を付ける。

- **カード表示**（現行。1件ずつじっくり）
- **一覧表示**（新設。行形式でまとめて確認）

一覧表示の仕様:

- 1行 = 明細1件。列: チェック / 日付 / 摘要 / 金額 / 勘定科目 / 税区分 / インボイス区分 / 提案の根拠
- 勘定科目・税区分・インボイス区分は**行の中で直接編集できる**（カードに戻らなくてよい）
- チェックできるのは**必須項目（勘定科目・インボイス区分）が埋まっている行だけ**
- 「チェックした◯件を登録する」ボタン → 確認ダイアログ1回（件数を表示）→ 実行

**実行の仕組み（ここが要点）:**

- クライアントが**チェックした行を1件ずつ順番に**既存の `action:'journalize'` へ送る
- **サーバー側は一切変更しない。** レート制限・仕訳済みチェック・インボイス必須・
  二重仕訳の事後検知・操作履歴（1件1行）がそのまま全部効く
- 行ごとに 成功／失敗 を表示。**失敗した行はスキップして続行**し、最後にまとめて表示
- **連続3件失敗したら自動停止**（MF側の障害時に無駄撃ちしない）
- 実行中は「中止」ボタンで止められる（送信済みの分は取り消さない。事実を表示）

**守る制限:**

- 1回の実行は**最大20行**まで（それ以上はチェックできない）
- **「全選択」ボタンは作らない。** チェックは行ごと（Shift+クリックの範囲選択は可）
- 一覧表示でも証憑の添付候補は出す（カード表示と同じ照合）が、
  一覧からの添付チェックは**完全一致（日付＋金額）の候補が1件だけの行**に限る

### 1.3 証憑候補の初期チェック（限定的に変更）

これまで「証憑候補のチェックは常に初期OFF」だった。中堅の指摘
「完全一致は自動チェックしても実害は小さい」を**条件付きで**採用する:

- **日付・金額が完全に一致する候補が、その明細に1件だけ**のとき → 初期チェックON
  （チェック済みであることが分かる色付きの印を付ける）
- それ以外（複数候補・日付ずれ・取引先名のみ一致）→ これまでどおり初期OFF

## 2. 事務所の管理（所長レビューの3指摘への対応）

### 2.1 税理士に「管理者」と「担当者」の役割を分ける

`tax_advisors` に `role` 列を追加: `'admin'`（事務所管理者＝所長）/ `'staff'`（担当者）。

- 役割の指定は**RIBRE側（⑤税理士の管理）**で行う。既定は `'staff'`
- `admin` の税理士には新タブ **「事務所の管理」** が出る

### 2.2 事務所の管理タブでできること（admin のみ）

| 機能 | 内容 |
|---|---|
| 職員の一覧 | 事務所の税理士アカウントと有効/無効・役割を表示 |
| 職員の招待 | 招待リンクを**事務所側でも発行できる**（7日・1回・取り消し可は同じ） |
| 職員の無効化 | `staff` を無効にできる（**即時に全操作が403になる**ことをサーバーで保証）。admin 同士は互いに無効化できない（RIBRE側のみ可能） |
| 操作履歴の全件閲覧 | これまで税理士は自分の操作しか見えなかった。admin は**事務所全員の操作**を見られる |
| 履歴のCSVエクスポート | §2.4 参照 |
| 承認の設定 | §2.3 参照 |

> これで所長レビューの「職員が辞めたとき、止められるのはRIBREであって私ではない」
> が解消される。**事務所側が自分で止め、止まったことを自分の画面で確認できる。**

### 2.3 承認ワークフロー（設定制・既定はOFF）

所長レビュー「職員が入れた仕訳が、私が確認する前に本番の帳簿へ入る」への対応。

`tax_workspace_settings` に `approval_policy` を追加: `'none'`（既定）/ `'required'`。
変更できるのは admin の税理士と RIBRE メンバー。

**`'required'` のときの流れ:**

1. `staff` の「この内容で登録する」は **「承認を依頼する」** に変わる
2. 入力内容（明細ID・勘定科目・税区分・インボイス区分・証憑の選択・メモ）を
   **そのまま** `tax_journal_requests` テーブルに保存する（MFへはまだ何も送らない）
3. admin の「承認待ち」一覧に、依頼者・内容・提案の根拠つきで表示される
4. admin が **承認** → サーバーが保存済みの内容で既存の `journalize` 処理を実行。
   操作履歴には**依頼者と承認者の両方**を記録する
5. admin が **差し戻し** → 理由（必須）つきで依頼者へ戻る。履歴にも残る

**安全性（既存の仕組みがそのまま効く）:**

- 承認の実行時にも「明細がまだ未仕訳か」を確認する（承認待ちの間に
  MFの画面で仕訳化されていたら `already_journalized` で止まる。既存実装のまま）
- admin 自身の登録は直接実行（自分が承認者のため）
- `'none'`（既定）なら現行どおり。**小規模事務所に承認の手間を強制しない**

新テーブル:

```sql
create table if not exists tax_journal_requests (
  id             bigint generated by default as identity primary key,
  requested_by   text not null,          -- 依頼した担当者
  transaction_id text not null,
  payload        jsonb not null,         -- journalize へ渡す内容そのまま
  status         text not null default 'pending',  -- pending / approved / rejected
  decided_by     text,                   -- 承認・差し戻しした人
  decided_reason text,                   -- 差し戻し理由
  decided_at     timestamptz,
  created_at     timestamptz not null default now()
);
-- RLSポリシーは作らない（service role のみ。既存テーブルと同じ方針）
```

### 2.4 監査証跡の独立コピー（所長レビュー「改ざんできないと言い切れない」への対応）

正直な前提: `tax_advisor_actions` は service role の鍵を持つ側（RIBRE）には
技術的に書き換え可能であり、**これはアーキテクチャ上なくせない**。

対応: **事務所側が独立したコピーを持てるようにする。**

- 操作履歴タブに **「CSVでダウンロード」** ボタンを付ける（admin は全件、staff は自分の分）
- ガイドに「月次で履歴をダウンロードして事務所側でも保管することを推奨します」と明記
- 事務所の手元にコピーがあれば、後から書き換えられても突き合わせで検出できる

（ハッシュチェーン等の改ざん検知は、この規模には過剰と判断して採用しない。
その判断も含めてガイドに正直に書く。）

## 3. 文言と用語の整備（新人レビューの全指摘）

### 3.1 ガイドに「用語の説明」の章を追加

| 用語 | 説明（案） |
|---|---|
| 勘定科目 | 取引を分類する名前です（通信費・支払手数料など）。**必須**。 |
| 補助科目 | 勘定科目をさらに細かく分けたものです。**空欄のままで問題ありません**。 |
| 税区分 | その取引に消費税がどうかかるかの分類です。任意です。消費税の金額はMFクラウド会計が自動で計算します。 |
| インボイス区分 | **必須**。適格＝適格請求書（インボイス）を受け取った取引／対象外＝消費税のかからない取引など／8割控除＝経過措置の対象。**迷ったときは登録せず、事務所の担当税理士にご確認ください**。 |
| 証憑（しょうひょう） | 領収書・請求書など、取引の証拠になる書類のことです。 |
| マッチ待ち | 証憑の添付先になる仕訳がまだ無く、できるのを待っている状態です。失敗ではありません。 |

⚠ 税務の正確な判断はガイドで断定しない。**「迷ったら担当税理士に確認」への誘導を必ず添える。**

### 3.2 「不安なら聞く」導線（全登録ボタンの共通文言）

登録ボタン直前の警告文に1文を追加する:

> ⚠ 登録するとMFクラウド会計に仕訳が作られます。この画面から取り消すことはできません。
> 間違えた場合はMFクラウド会計の仕訳帳から編集・削除してください。
> **内容に自信が持てないときは、登録せずに事務所の先輩・担当の税理士にご確認ください。**

### 3.3 提案（前回と同じ科目）の文言を強化

現行: 「前回の仕訳から入れています。確認してください。（過去5件中3件・最終 2026/7/15）」

改訂: 数字の意味と「正しいとは限らない」を明示する。

> 前回の仕訳から**自動で**入れています。過去5件のうち3件がこの内容でした
> （**残り2件は別の内容でした**）。自動で選んだだけで正しいとは限りません。
> ご自身で確認してから登録してください。

### 3.4 決算済み期の警告に相談への誘導を追加

> ……この期の帳簿はすでに確定している可能性があります。
> **このまま登録してよいか自信が持てない場合は、登録せずに担当の税理士・先輩にご確認ください。**

### 3.5 ⑦現金払いの「貸方」の使い分け

⚠ 前回のモックで貸方の例に「事業主借」を使っていたが、**これは個人事業主の科目**。
対象は株式会社（法人）なので不適切だった（今回の設計見直しで発見）。
選択肢は**MFの勘定科目マスタから実在するものだけ**を出し、例示は法人の科目にする:

> 貸方（お金の出どころ）は次を目安に選んでください。分からない場合は登録せず、担当の税理士にご確認ください。
> ・会社の現金で支払った → **現金**
> ・役員が自分のお金で立て替えた → **役員借入金**（または未払金。事務所の方針に従ってください）
> ・まだ支払っていない（後払い） → **未払金**

### 3.6 ⑧「証憑不要」の判断例

> 例: 振込手数料・受取利息・売掛金の入金・口座間の振替など、
> **性質上そもそも領収書等が存在しない取引**は「証憑不要」として構いません。
> これは一般的な例であり、最終的なご判断は税理士さまにお願いします。
> 判断に迷う取引は空欄のままにして、後日まとめてご確認ください。

### 3.7 そのほかの文言（新人レビューの小粒指摘）

- 登録ボタンの下に**常時**「勘定科目とインボイス区分を選ぶと押せます」を表示
  （現在はマウスを乗せたときのツールチップのみ）
- 登録成功メッセージに**仕訳番号**を出す:
  「登録しました（**仕訳番号 751**）。MFクラウド会計の仕訳帳でこの番号で確認できます。」
  ※ `journalize` の応答（`CRUDJournalResponse` → `JournalItem.number`）に番号が含まれることは確認済み
- ログイン画面に「**初めての方は『新規登録』→ そのあと『ログイン』の2段階です**」を明記
- ②仕訳待ちの証憑タブ: 件数だけでなく**ファイル名・日付・金額の一覧**を出す

## 10. 再レビュー（2026-08-04・2回目）で追加された要件

3視点の再レビュー結果: **前回の重大指摘はすべて解消判定**
（新人: 11項目中8解消・3は本実装時に確認／中堅: 「100件の月でも使える見込みが立った」／
所長: 「承認制ONなら限定した職員への展開を検討してよい段階」）。
そのうえで出た追加要件。**本実装時に必ず反映する。**

### 10.1 一括確認リストの詰め（中堅・新人）

1. **連続3件失敗の数え方**: 通信・サーバーエラー（5xx・タイムアウト）だけを数える。
   `already_journalized`（MF画面で先に仕訳化されていた＝正常なすれ違い）は
   **「スキップ（想定内）」として区別**し、失敗カウントに入れない。
   口座連携主体の運用では同じ取引先がまとまって仕訳済みのケースが普通に起きるため
2. **20行上限はチェックの時点で効かせる**: 20件に達したら残りのチェックボックスを
   無効化し、「20/20」のカウンターを常時表示する（押してから弾かない）
3. **一覧にも行ごとの「クリア」**（提案を空に戻す）を付ける
4. **提案の視覚的な強弱**: 一致率が低め（6〜8割）の行は根拠を黄色系の表示にし
   「要確認」のバッジを付ける。全行が同じ濃さの文字だと「入っているから合っている」と
   流されやすい（新人レビューの核心的指摘）
5. **キーボードだけの範囲選択**: フォーカス行で Shift+↓/↑ によりチェック範囲を
   伸ばせるようにする（Shift+クリックはマウスが要るため）
6. 一覧表の直前に「自動で入れた下書きであり正しいとは限らない」旨の注意を常時表示
   （モックには反映済み）

### 10.2 承認ワークフローの詰め（所長・中堅・新人の指摘が一致）

1. **承認実行時に内容の再確認**: 依頼時に保存した明細の金額・日付・摘要と、
   実行時点の明細を突き合わせ、**変わっていたら実行せず**にadminへ差分を表示する
   （§7 P6-B の解決。`already_journalized` 判定に加えて行う）
2. **承認・差し戻しも `tax_advisor_actions` に記録する**
   （action: `approve_journalize` / `reject_journalize`、差し戻し理由を含む）。
   **CSVエクスポートにも含める**（税務調査で「なぜ差し戻されたか」も聞かれうる）
3. **依頼者への結果通知**: 承認・差し戻しの結果を依頼者が見に行かなくても
   分かるようにする。最低限、ログイン時に「あなたの依頼が承認/差し戻しされました」の
   表示を出す。Chatwork通知（既存インフラあり）への連携は任意で検討
4. ガイドに **「admin役割は所長本人か、真に信頼できる最小人数に限定してください」**

5. ガイドに **「新人・担当者が使い始める期間だけでも承認をONにすることを推奨」** を明記
   （承認が一番効く時期に既定OFFのままだと機能しない、という新人レビューの指摘）
