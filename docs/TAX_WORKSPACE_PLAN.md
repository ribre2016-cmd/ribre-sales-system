# 税理士ワークスペース 設計書

作成: 2026-08-02 / 状態: **設計のみ。実装は未着手**

税理士向け共有ページ（`tax-share.html`）を、ファイルを渡すだけの場から
「税理士がそのままMFへ仕訳登録できる作業画面」へ広げる案。

このファイルは**根拠のある事実**と**未確認の事項**を明確に分けて書く。
未確認の項目は実測するまで実装しない。

---

## 1. まず正直な前提: 税理士はすでにMFに入れる

利用者への確認（2026-08-02）で、**税理士はMFクラウド会計にメンバー招待済みで直接ログインできる**
ことが分かっている。つまりMFの「自動で仕訳」画面で仕訳登録も証憑添付もすでにできる。

したがってこの画面は **必須ではなく、作業を楽にする層**である。
作る価値があるかは、MFの画面に対して何が増えるかで判断する。

### MFの画面に対して増えるもの（＝作る理由）

| 増えるもの | 内容 |
|---|---|
| **共有ファイルが同じ画面にある** | 給与明細・ヤマト請求書・オークション精算書・売上管理表Excelなど、税理士へ渡しているファイルはMFのBoxには入っていない。明細を見ながらその根拠資料を開ける |
| **登録と証憑添付が1操作** | MFでは仕訳を登録してから証憑を紐付ける2操作になる。ここでは登録の直後に添付まで通す |
| **売上管理システム側の数字を横に出せる** | チャネル別売上・仕入・送料など、MFには無い情報 |
| **「マッチ待ち」の証憑を税理士側から解消できる** | 仕訳が無いために送信を保留している証憑（例: 2026-07-13 Vercel）が一覧で見え、その場で仕訳を作れば解消する |

### 増えないもの（＝MFでやった方が早いこと）

- 複雑な複合仕訳、決算整理、修正申告
- 試算表・推移表の閲覧（MFの方が高機能）
- 明細の取込設定、連携口座の管理

**この画面は「明細1件を仕訳にして証憑を付ける」ことに絞る。**
それ以外はMFへ誘導する。範囲を広げるとMFの劣化コピーになる。

### 比較検討した安い代替案

共有しているファイルを**MFクラウドBoxへ入れてしまえば**、税理士はMFの中だけで完結する。
新画面は不要になる。ただし
- Boxへの投入はMFの証憑APIが `journal_id` 前提のため、未紐付けで入れると回収できない
  （`DELETE /vouchers` は `journal_id` 必須。§2の確認結果を参照）
- 給与明細やExcelなど「仕訳に紐づかない参考資料」はBoxに置き場が無い

ため、共有ページ自体は残す必要がある。**この代替案では置き換えられない。**

## 2. 確認済みの事実（MF公式OpenAPI仕様書）

出典: `https://developers.api-accounting.moneyforward.com/v3/openapi.yaml`（2026-08-02取得・21万文字）

### 2.1 明細から仕訳を作るAPIは単純

`POST /api/v3/transactions/journalize`（scope: `mfc/accounting/journal.write`）

| パラメータ | 必須 | 内容 |
|---|---|---|
| `transaction_id` | ✅ | 仕訳化する明細のID |
| `account_id` | ✅ | 勘定科目ID |
| `tax_id` | | 税区分ID |
| `sub_account_id` | | 補助科目ID |
| `department_id` | | 部門ID |
| `trade_partner_code` | | 取引先コード |
| `invoice_kind` | | `INVOICE_KIND_NOT_TARGET` / `_QUALIFIED` / `_UNQUALIFIED_80` |
| `transaction_date` | | 未指定なら明細の取引日 |
| `memo` / `tags` | | |

**相手勘定は指定しない。** 連携口座側（普通預金・未払金など）はMFが決める。
MFの「自動で仕訳」画面と同じ挙動。

**成功時 201 で `CRUDJournalResponse` を返す＝作成された仕訳のIDが分かる。**
そのIDを `POST /vouchers` に渡せば、登録の直後に証憑を添付できる。

### 2.2 これは既存設計書の最大の課題を回避する

`docs/MF_JOURNAL_PLAN.md` では「消費税の丸めをアプリ側で再現できるか」が
未解決の最重要事項（A1〜A3の実測待ち）だった。

`journalize` は**金額と税区分を渡すだけで、税額の計算はMF側が行う**。
アプリが消費税を計算しないので、この課題に触れずに済む。

⚠ ただし **§6の未確認事項A** を実測するまでは断定しない。

### 2.3 手で仕訳を作るAPI（明細が無い場合）

`POST /api/v3/journals`（scope: `journal.write`）
`CRUDJournalRequest`: `journal.transaction_date` / `journal_type` / `branches`（1〜300行）が必須。
各 `branches[]` は `remark` と `debitor` / `creditor`。各サイドは `account_id` と `value` が必須。

**Phase 1では使わない。** 明細からの仕訳化だけに絞る（§4）。

### 2.4 証憑の添付・解除

- `POST /api/v3/vouchers`: `journal_id`(nullable) + `voucher_files`。**`transaction_id`は受け付けない**
- `DELETE /api/v3/vouchers`: `journal_id` と `voucher_file_id` の**両方が必須**
  → 仕訳に紐づいていないファイルは解除できない＝未紐付けで上げると回収不能
- `Transaction.voucher_file_ids` は取得専用。**明細に証憑を添付するAPIは存在しない**

### 2.5 選択肢に使うマスタ

| API | scope | 実データ |
|---|---|---|
| `GET /accounts` | `accounts.read` | 勘定科目 |
| `GET /sub_accounts` | `accounts.read` | 補助科目 |
| `GET /taxes` | `taxes.read` | **80件超**（課売10%一〜六種、課仕10%、輸入仕入、返還等、貸倒…） |
| `GET /trade_partners` | `trade_partners.read` | 取引先 |
| `GET /departments` | `departments.read` | 部門 |

⚠ **税区分80件超をそのまま並べる選択欄は作らない。** 実務で使うのはごく一部。
実際の仕訳から使用頻度を数えて上位を既定にする（§3.3）。

### 2.6 制限

- **1秒あたり3リクエストまで**（ClientID × 事業者ID）。出典: `/rate_limiter`
- 仕訳は最大300行
- 仕訳の削除は `DELETE /api/v3/journals/{id}`（scope: `journal.write`）

### 2.7 追加が必要なスコープ

現在の `MF_SCOPE`（`api/mf/_lib/mf-client.js`）:
`voucher.write` / `journal.read` / `transaction.read`

追加が必要:
`journal.write` / `accounts.read` / `taxes.read` / `trade_partners.read`
（部門を使うなら `departments.read`）

**スコープを増やすと既存トークンでは足りず、再連携が必要になる。**
再連携するまで新機能だけが403になり、他機能は動き続ける実装にすること
（`api/mf/awaiting-reason.js` の403ハンドリングと同じ方式）。

## 3. 画面設計

新ページ `tax-workspace.html`。共有ページ（`tax-share.html`）とは**別ページ**にする。
共有ページはログイン不要のまま残す（ファイルを渡すだけの用途は今のままでよい）。

### 3.1 全体構成

```
┌─────────────────────────────────────────────────────┐
│ 税理士ワークスペース   ログイン中: <税理士のメール>  [ログアウト] │
│ 対象月 [2026-07 ▼]                                    │
├─────────────────────────────────────────────────────┤
│ ① 未仕訳の明細（この画面のメイン）                     │
│ ② 仕訳待ちの証憑                                      │
│ ③ 共有ファイル                                        │
│ ④ 操作履歴                                            │
└─────────────────────────────────────────────────────┘
```

### 3.2 ① 未仕訳の明細（メイン）

`GET /transactions?journalizing_statuses=none` の結果を1件1カードで表示。

```
┌───────────────────────────────────────────────────────┐
│ 2026-07-13  VERCEL INC.              支出 3,362円      │
│ アメリカン・エキスプレスカード                          │
│                                                        │
│ 勘定科目 [通信費        ▼]  補助科目 [なし    ▼]        │
│ 税区分   [課仕 10%      ▼]  インボイス [適格   ▼]       │
│ 取引先   [              ▼]  メモ [                  ]  │
│                                                        │
│ 関連しそうな証憑                                        │
│  ☑ 20260713_Vercel Inc._20USD.pdf   [👁 プレビュー]    │
│    ※取引先名と日付(±45日)で見つけた候補。金額は照合して  │
│      いません（外貨のため）。中身を確認してください      │
│                                                        │
│                        [ この内容で登録する ]           │
└───────────────────────────────────────────────────────┘
```

**証憑の候補**は既存の `api/mf/awaiting-reason.js` の `transactionMatchesEvidence` を使う。
明細の `content` と証憑の `ocr_vendor` を語単位（`vendorTokens`）で突き合わせ、日付±45日で絞る。
⚠ `mf-match-core.js` の `findVendorDateCandidates` は**仕訳(journals)を相手にする関数**なので
ここでは使えない（2026-08-02のレビューで取り違えを修正）。

**自動でチェックは入れない。** 税理士が中身を見て選ぶ。

**添付できるファイルの形式には制限がある。**
`api/mf/ingest-mail.js` の `ALLOWED_CONTENT_TYPES` は `image/png` / `image/jpeg` /
`application/pdf` の3種のみ。**Excel(.xlsx)は証憑として添付できない。**
共有ファイルの主力である売上管理表Excelは対象外で、③共有ファイルタブで見るだけになる。
MF側がxlsxを受け付けるかは**未確認（§6-F）**。確かめるまで対応形式を広げない。

**候補に出す証憑の範囲**は次の2つ。
1. 証憑台帳（`mf_evidence`）のうち、まだ仕訳に添付されていないもの
2. 共有ファイル（`tax-docs` バケット）のうち **PDF・PNG・JPEG のもの**
   （給与明細PDF・請求書PDFなど。Excelは除く）

**「登録する」を押したときの処理（サーバー側で直列に実行）**

1. その明細がまだ `journalizing_status = none` かを `GET /transactions` で確認 → 既に仕訳済みなら拒否
2. `POST /transactions/journalize` → 201なら `journal.id` を得る
3. 証憑が選ばれていれば `POST /vouchers`（`journal_id` + ファイル本体）
4. 操作履歴に記録（誰が・いつ・どの明細を・どの科目で・証憑を付けたか）
5. 画面のカードを畳んで「登録しました」に置き換える

⚠ 手順3が失敗しても**手順2は取り消さない**。仕訳は既にできているので、
「仕訳は登録済み・証憑の添付だけ失敗」と正確に表示し、証憑は再試行できるようにする。
勝手に仕訳を消すと、税理士が知らないうちに帳簿が変わる。

### 3.2.1 月締めとの関係（止めない・警告だけ）

売上管理システムの「月締め」は**売上データのロック**であって、MFの仕訳とは別物。
税理士は締めた後に決算整理仕訳を入れるのが普通なので、**登録は止めない**（利用者判断 2026-08-02）。

対象月が締め済みのときは、画面に
「この月の売上は締め済みです。仕訳を追加すると売上管理側の数字と差が出る場合があります」
と**表示するだけ**にする。

⚠ 当初は「締め済みなら登録を拒否」と書いていたが、次の2点で撤回した。
- 月締め状態は `appvIsMonthClosed()` がブラウザ内の売上行のメモ（`[LOCK]`）を見て判定しており、
  サーバー側に同等の手段が無い（実装できない指示だった）
- そもそも税理士の作業を止めるのは実務に合わない

画面表示用の締め状態は、クライアントが既存の `appvIsMonthClosed()` 相当で判定する。
**サーバー側の登録処理はこの判定に依存しない。**

### 3.3 選択欄の作り方（税区分80件超への対応）

⚠ **これはPhase 4の機能**（§8）。Phase 1〜3では選択欄の初期値は**すべて未選択**にし、
税理士が毎回選ぶ。学習は動作が安定してから足す。

1. 起動時に `GET /journals`（過去12ヶ月）を読み、**実際に使われている
   勘定科目・税区分の組み合わせを頻度順に集計**する
2. その明細の取引先名（`content`）が過去の仕訳の摘要と一致するものがあれば、
   **前回と同じ科目・税区分を初期値**として入れる（例: VERCEL INC. → 通信費 / 課仕10% / 適格）
3. 選択欄は「よく使う」を上に、区切り線の下に全件。検索入力つき

⚠ **初期値はあくまで下書き。** 「前回と同じ」であって「正しい」ではない。
画面に「前回の仕訳から入れています。確認してください」と明示する。

### 3.4 ② 仕訳待ちの証憑

`status='awaiting_match'` の証憑を並べる。今日の実例（Vercel・Anthropic）のように、
仕訳が無いために送信を保留しているもの。①で仕訳を作れば解消する。

### 3.5 ③ 共有ファイル

現在の `tax-share.html` と同じ一覧＋プレビュー＋ダウンロード済み表示。

### 3.6 ④ 操作履歴

誰がいつ何を登録したかを全件表示。**削除できない追記専用**。
§5-5のとおり、これがこの機能の**唯一の監査証跡**になる。

```sql
create table if not exists tax_advisor_actions (
  id             bigint generated by default as identity primary key,
  actor_email    text not null,        -- 操作した税理士
  action         text not null,        -- 'journalize' など
  transaction_id text,                 -- 対象の明細ID
  journal_id     text,                 -- 作成された仕訳ID
  account_id     text,
  tax_id         text,
  evidence_ids   text[],               -- 添付した証憑
  result         text not null,        -- 'ok' / 'journal_ok_voucher_failed' / 'failed'
  error_message  text,
  payload        jsonb,                -- 送信内容そのまま（後から検証できるように）
  created_at     timestamptz default now()
);
alter table tax_advisor_actions enable row level security;
-- 参照: 社内メンバーと、本人（税理士）のみ
-- 追加: ポリシーを作らない（service roleのサーバー側だけが書く）
-- 更新・削除: ポリシーを作らない（追記専用にするため）
```

⚠ 保持期間は**削除しない**。件数は多くても年間数千行で問題にならない。

## 4. 認証設計

利用者の判断（2026-08-02）: **税理士専用ログインを作って直接登録できるようにする**。

### 4.1 なぜ共有リンクのままではいけないか

共有ページはURLのトークンだけで開ける。メールの転送・誤送信・端末の紛失で
リンクが漏れれば、**知っている人が誰でも帳簿に仕訳を作れる**ことになる。
ファイルの閲覧とは危険度が違う。

### 4.2 方式

- Supabase Auth のメール＋パスワード（既存のログイン基盤をそのまま使う）
- **役割の許可リスト**をテーブルで持つ（`tax_advisors`: email, 有効/無効, 追加日）
- 書き込みAPIは**すべてサーバー側**で、リクエストごとに
  「ログイン済み」かつ「許可リストにいる」ことを検証する
- 許可リストからの削除で即座に権限が切れる

### 4.2.1 auth-gate に入口の許可リストを足す（必須）

現状の `services/auth-gate.js` は **「ログインしていれば通す」だけで許可リストが無い**。
税理士アカウントを同じSupabase Authに作ると、**売上管理システム本体の画面も開けてしまう**。

データが漏れるわけではない（レビューで確認済み）:

| 対象 | 守られ方 |
|---|---|
| `sales` / `purchases` | RLSが `user_email = auth.jwt() ->> 'email'` なので、税理士のメールでは0件 |
| `mf_evidence` | `supabase_mf_owner_rls.sql` の会員許可リストで弾かれる |
| `mf_tokens`（MFのアクセストークン） | **ポリシーを一切作っていない**ため authenticated からは読めない（service roleのみ） |

ただし空の本体画面が開けてしまい、税理士が自分のメールでデータを作れる状態は混乱の元。
利用者判断（2026-08-02）で **auth-gate に入口の許可リストを足す**。

- 本体の画面（`index.html` ほか）: 社内メールのみ
- 税理士ワークスペース（`tax-workspace.html`）: 税理士メールのみ
- 共有ページ（`tax-share.html`）: 従来どおりログイン不要

⚠ auth-gate は静的サイトの画面ガードにすぎない（ファイル冒頭のコメントのとおり）。
**本当の防御はRLSとサーバー側の検証**であり、許可リストは誤って入る事故を防ぐためのもの。

### 4.3 税理士に見せないもの

- 売上管理システム本体（取引・仕入・スタッフ名簿・設定）
- MFの接続設定・トークン
- 他社のデータ（Supabaseプロジェクトは他アプリと共用のため、
  `tax_advisors` の判定は必ずこのアプリのテーブルに閉じる）

## 5. 安全装置（これを実装しないならリリースしない）

1. **月締め済みの月は警告を出す**（登録は止めない。§3.2.1の判断）
2. **1回の操作で1件だけ。一括登録は作らない**（間違いが一気に広がる）
3. **レート制限3req/secを守る**。サーバー側で直列実行し、429は指数バックオフで再試行。
   ⚠ 制限は **ClientID × 事業者ID** 単位なので、`api/mf/auto-match.js` のcronと
   食い合う。**MFを叩く処理はすべて共通のスロットルを通す**こと
   （税理士の操作中にcronが走って429になる事故を防ぐ）。
   cronの実行時間帯と税理士の作業時間が重なりうる前提で設計する
4. **同じ明細を二重に仕訳化しない（完全には防げない前提で作る）**。
   登録前に `GET /transactions` でその明細がまだ `none` かを確認するが、
   確認と登録の間にMFの画面側で仕訳化されると二重になる（TOCTOU）。
   MFに冪等キーは無いため、**登録後にもう一度 `GET /journals` で
   同じ `transaction_id` を持つ仕訳が複数無いかを確認し、あれば画面に警告を出す**。
   自動では消さない（消す判断は税理士）
5. **操作履歴は追記専用**。誰が・いつ・何を登録したかを必ず残す。
   ⚠ **MF側では誰が作ったか分からない**。仕訳はアプリのOAuthトークンで作られるため、
   MFの記録上はすべて同じ「連携アプリ」になる。税理士個人を特定できるのは
   こちらの操作履歴だけなので、**この履歴が唯一の監査証跡**になる
6. **取り消しは作らない（Phase 1）**。§6の未確認事項Bが分かるまで、
   間違えた場合はMFの画面で修正してもらう
7. **金額はアプリで計算しない**。明細の金額をそのまま使い、税額はMFに計算させる
8. 登録処理は**証憑の添付に失敗しても仕訳を取り消さない**（§3.2）

## 8. フェーズ計画

| Phase | 内容 | 前提 |
|---|---|---|
| **0** | この設計書とモック画面のレビュー | — |
| **1** | auth-gateの許可リスト＋`tax_advisors`＋`tax_advisor_actions`＋**読み取りのみ**の画面（未仕訳明細・証憑・共有ファイルを見るだけ） | 税理士の了解、**スコープ追加と再連携** |

⚠ **スコープ追加と再連携はPhase 1で必要**（当初はPhase 3の前提と書いていたが誤り）。
選択欄に勘定科目・税区分を出す時点で `accounts.read` / `taxes.read` が要るため。
`journal.write` はPhase 3まで使わないが、再連携を2回させないためPhase 1でまとめて取得する。

**Phase 3に進む前に、必ずPhase 2の実測結果をこの設計書へ追記する。**

### 8.1 未解決のまま残す事項（実装を止めるものではない）

- **税理士が複数人になった場合**の想定。`tax_advisors` は複数行を許すので技術的には対応済みだが、
  「他の税理士が登録した仕訳が見えてよいか」は未確認。Phase 1では全員が全部見える前提で作り、
  必要なら後で絞る
- **間違って登録した直後の救済**。Phase 1〜3では取り消しを作らない（§6-B が未確認のため）。
  画面には「間違えたらMFの画面で修正してください」と明示し、対象の仕訳へのリンクを出す
