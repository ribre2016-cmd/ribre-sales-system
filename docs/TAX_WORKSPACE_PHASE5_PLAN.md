# 税理士ワークスペース Phase 5 設計書（未仕訳の訂正・証憑の紐付け・現金払い）

作成: 2026-08-04 / 状態: **設計とモックのみ。実装は未着手**

Phase 1〜4（`docs/TAX_WORKSPACE_PLAN.md`）の続き。
利用者からの4つの要望と、税理士実務の観点で追加提案する機能をまとめる。

このファイルも**根拠のある事実**と**未確認の事項**を分けて書く。

---

## 0. 先に結論: できること・できないこと

MF公式OpenAPI仕様書（`https://developers.api-accounting.moneyforward.com/v3/openapi.yaml`）で確認した。

| やりたいこと | API | 可否 |
|---|---|---|
| 未仕訳明細を仕訳登録する | `POST /transactions/journalize` | ✅ **実装済み**（Phase 3） |
| 登録前に勘定科目・税区分などを決める（＝訂正） | 同上のパラメータ | ✅ **実装済み** |
| 登録**後**の仕訳を訂正する | `PUT /api/v3/journals/{id}` | ✅ **できる**（未実装） |
| 登録済みの仕訳に証憑を後から付ける | `POST /vouchers`（`journal_id`指定） | ✅ **できる**（未実装） |
| 明細が無い取引（現金払い）の仕訳を作る | `POST /api/v3/journals` | ✅ **できる**（未実装） |
| 仕訳を削除する | `DELETE /api/v3/journals/{id}` | ✅ できる（作らない方針） |
| **明細を「対象外」にする** | — | ❌ **APIに存在しない** |
| 明細の摘要を書き換える | — | ❌ **APIに存在しない** |

### ❌「対象外」ボタンだけは作れない

利用者のスクリーンショットにあるMFの「対象外」ボタンに相当するAPIが**無い**。
`journalizing_statuses` の `excluded` は**検索の絞り込み値としてしか定義されておらず**
（`GET /transactions` のクエリパラメータと `Transaction` スキーマの読み取り専用フィールド）、
状態を書き換えるエンドポイントは仕様書のどこにも無い。
`POST /transactions` は明細の**新規作成**であり、既存明細の状態変更はできない。

→ **手順書と画面に明記し、MFの該当画面へのリンクを出す**（§5）。

## 1. 共有ファイルを「証憑」と「参考資料」に分ける

### 現状の問題

`api/mf/tax-workspace.js` の `ATTACHABLE_EXT_RE` は**拡張子だけ**で判定している。

```js
const ATTACHABLE_EXT_RE = /\.(pdf|png|jpe?g)$/i;
```

つまり **PDFなら何でも「証憑添付可」**になる。しかし利用者の指摘のとおり、
共有ファイルには「税理士に渡すだけの資料」も入っている。

実例（実際に共有されているファイル）:

| ファイル | 本来の扱い | 現状の判定 |
|---|---|---|
| `オークション志木_20260710_ver1_精算書.pdf` | 証憑 | 証憑添付可 ✅ |
| `ヤマト請求書_56510_20260731.pdf` | 証憑 | 証憑添付可 ✅ |
| `給与支給明細一覧表(令和8年7月支給).pdf` | **参考資料**（仕訳に添付するものではない） | 証憑添付可 ❌ |
| `2026年7月支給給与支給明細書(◯◯様).PDF` | **参考資料**（個人の明細） | 証憑添付可 ❌ |
| `物販売上管理表26_10期.xlsx` | 参考資料 | 閲覧のみ ✅ |

### 設計

ファイルごとに**区分**を持たせる。判定を拡張子任せにしない。

- 保存先: 既存の `app_settings`（`skey='tax_docs_index'`）の `files[<key>]` に `kind` を追加
  - `'evidence'` … 証憑。仕訳への添付候補に出る
  - `'reference'` … 参考資料。**閲覧のみ**。添付候補に出さない
- **既定は `'reference'`**（安全側）。何も設定していない既存ファイルは参考資料として扱う
  → 添付されるべきものが出てこないのは「気づいて直せる」が、
    添付されるべきでないものが候補に出るのは「気づかず添付してしまう」ため
- 区分は**オーナーが売上管理システムの「税理士送付ファイル」カードで設定する**
  （税理士に区分の判断をさせない。何を証憑として扱うかは会社側の整理）
- 拡張子の制限は残す。`.xlsx` 等は `kind` に関わらず添付不可（`ALLOWED_CONTENT_TYPES`）

⚠ **既存ファイルを一括で `'evidence'` にしない。** 給与明細まで添付候補に出てしまう。

## 2. 未仕訳明細の訂正・登録（MFの画面に近づける）

### 現状できていること

Phase 3で**登録はできる**。勘定科目・補助科目・税区分・インボイス区分・メモを選んで登録する。
「登録前に内容を決める」＝実質的に訂正なので、利用者の要望の大半は**すでに満たされている**。

### 現状足りないもの（MFの画面と比べて）

| MFの画面にある | この画面 | 対応 |
|---|---|---|
| 勘定科目・補助科目 | ✅ ある | — |
| 税区分・インボイス区分 | ✅ ある | — |
| 取引先 | ❌ 無い | **不要**。`GET /trade_partners` が0件で、摘要に取引先名を入れる運用（実測済み） |
| タグ | ❌ 無い | **追加する**。`journalize` の `tags` で送れる（仕様書で確認） |
| 摘要の編集 | ❌ 無い | **できない**。APIに明細の摘要を書き換える手段が無い |
| 「対象外」 | ❌ 無い | **できない**（§0）。MFの画面へ誘導する |
| 一括登録 | ❌ 無い | **意図的に作らない**（設計書§5-2・§9-2） |

### 追加する: タグ

`POST /transactions/journalize` の `tags`（20文字以内の配列）。
過去の仕訳で使われているタグを候補に出す（`GET /journals` の `tags` から集計）。

### 登録済み仕訳の訂正（新規）

`PUT /api/v3/journals/{id}` で可能。ただし**リクエストは仕訳全体の置き換え**
（`CRUDJournalRequest`＝`transaction_date` / `journal_type` / `branches` が必須）で、
部分更新ではない。つまり**貸方も含めて全部を組み立て直す**必要がある。

⚠ これは危険度が上がる。誤ると相手勘定まで書き換わる。

**Phase 5では実装しない。** 理由:
- 訂正はMFの仕訳帳から編集できる（Phase 2で確認済み。「編集」ボタンあり）
- 全体置き換えのAPIで部分訂正を作ると、意図しない側を壊す事故が起きやすい
- 「間違えたらMFで直す」という既存の方針（`TAX_WORKSPACE_PLAN.md` §5-6）と整合

画面には「登録した仕訳の訂正はMFクラウド会計の仕訳帳から行ってください」と明記し、
**その仕訳へのリンク**を出す（登録直後のメッセージにも入れる）。

## 3. 登録済み仕訳への証憑の紐付け（⑥タブ・新規）

### 何を解決するか

利用者の指摘のとおり、**口座・カード連携をしているので取引の大半はMFの未仕訳に入る**。
税理士がMFの画面で先に仕訳登録してしまうと、こちらの証憑は「マッチ待ち」に残る。
また、証憑が後から届く取引（請求書が翌月）もある。

既存の証憑インボックス（`mf-evidence.html`）にはこの機能があるが、
**オーナー専用**で税理士は使えない。同じことを税理士ワークスペースからできるようにする。

### 設計

⑥タブ「証憑の紐付け」

**左: 添付先の無い証憑**
- 証憑台帳（`mf_evidence`）で `status` が `pending` / `awaiting_match` のもの
- 共有ファイルのうち `kind='evidence'` かつ PDF・画像のもの（§1）

**右: 候補の仕訳**
- 既存の照合ロジックをそのまま使う（`api/mf/_lib/mf-match-core.js`）
  1. 完全一致（取引日＋金額）
  2. 日付±14日（金額一致）
  3. 取引先名＋日付±45日（**金額は照合しない**。外貨建て向け）
- 候補が出たら「この仕訳に添付」。**自動では添付しない**（Phase 3と同じ）

**制限（既存の制約をそのまま引き継ぐ）**
- 1つの仕訳に添付できる証憑は**5件まで**（`MAX_VOUCHER_FILES_PER_JOURNAL`）
- 添付は**取り消せない**（MFのvouchers APIは呼ぶたびに新規ファイルを作る）
  → 画面に必ず明示する
- 送信前に必ずDBをclaimしてから送る（既存の `attachEvidenceToJournal` を使う）

## 4. 現金払い: 領収書のOCR → 手動仕訳 → 証憑添付（⑦タブ・新規）

### 何を解決するか

現金払いは口座・カード連携に乗らないため**MFの未仕訳にも出てこない**。
今は誰かが手で仕訳を作り、別途証憑を用意している。

### 設計

⑦タブ「現金払いの登録」

1. 領収書の画像・PDFをドラッグ＆ドロップ（または貼り付け）
2. **OCR**（既存の仕組みを流用: `api/openai/responses` + `gpt-4.1`）で
   日付・金額・取引先・通貨を読む
   ⚠ 既存の制約をそのまま守る（`CLAUDE.md` 制約#17）:
   **想定外の形（配列・複数候補）で返ったら黙って失敗させ、手入力に委ねる。
   「それらしい値」を合算などで作らない**（過去に架空の金額を出した実例あり）
3. 読めた値を**確認・修正できる欄**に出す（OCRは下書き。必ず人が確認）
4. 借方（費用の科目）と**貸方**を選ぶ
   ⚠ 明細が無いのでMFは相手勘定を決めてくれない。**貸方も選ぶ必要がある**
   （現金／事業主借／未払金 など。既定値は入れない）
5. `POST /api/v3/journals` で仕訳を作る
6. 返ってきた仕訳IDで `POST /vouchers` に領収書を添付

### 守ること

- **借方1行・貸方1行の単純な仕訳だけ**にする。複合仕訳は作らせない
  （`branches` は最大300行だが、複雑な仕訳はMFの画面で作るべき）
- 金額は**OCRの値をそのまま**使い、**消費税はアプリで計算しない**
  （Phase 2の実測どおりMFに計算させる）
- インボイス区分は**必須**（Phase 4と同じ方針）
- 証憑の添付に失敗しても仕訳は取り消さない（Phase 3と同じ）
- 操作履歴に必ず記録する

### 未確認事項（実装前に確かめる）

| # | 内容 |
|---|---|
| **P5-A** | `POST /journals` で作った仕訳でも、税額はMFが計算してくれるか（`journalize` では実証済みだが、こちらは `value` を直接渡すため**税抜で渡すのか税込で渡すのか**が違う可能性がある）。**これは実測しないと分からない。最重要** |
| **P5-B** | `POST /journals` の `branches[].debitor.value` は税抜か税込か |
| **P5-C** | 手動仕訳に `transaction_id` は付かないため、二重登録の事後検知（Phase 3の仕組み）が使えない。別の重複検知（同日・同額・同摘要）が要るか |

⚠ **P5-A・P5-B が分かるまで現金払いの機能は実装しない。**
消費税の扱いを間違えると帳簿が狂う。Phase 2と同じく、小さい金額で1件試して確かめる。

## 5. できないことを手順書に明記する

`tax-guide.html` に「この画面でできないこと」の節を追加する。

| できないこと | どうするか |
|---|---|
| 明細を「対象外」にする | MFクラウド会計の「連携サービスから入力」画面で操作してください（APIに機能がありません） |
| 明細の摘要を書き換える | 同上 |
| 登録した仕訳を訂正・削除する | MFクラウド会計の「仕訳帳」から編集・削除してください |

| 一括登録 | ありません。1件ずつ確認して登録してください（意図的な仕様） |

各項目に**MFの該当画面へのリンク**を添える。

## 6. 税理士実務の観点で追加提案する機能

利用者から「他にも作業が楽になる機能があれば」との依頼。
**MFにある機能をわざわざ作り直さない**という原則（`TAX_WORKSPACE_PLAN.md` §1）を守り、
「MFには無い／MFでは面倒」なものだけを挙げる。

### 6.1 証憑が付いていない仕訳の一覧 【推奨度: 高】

電子帳簿保存法の対応で「どの仕訳に証憑が要るか」は税理士の判断。
`GET /journals` の `voucher_file_ids` が空の仕訳を月ごとに一覧し、
**「証憑不要」の印を付けられる**ようにする（印はこちらのDBに持つ。MFには書かない）。

- 既存の「証憑カバー率」（`api/mf/coverage.js`）は**全仕訳が分母**で、
  売掛金の回収・振込手数料・受取利息まで数えるため実用にならなかった（2026-08-02の判断）
- 税理士が「これは証憑不要」と印を付けていけば、**残ったものが本当の未対応**になる
- これはMFに無い。**この画面を作る一番の価値かもしれない**

### 6.2 「この取引は何ですか？」の質問メモ 【推奨度: 高】

税理士が判断できない取引について、明細ごとに質問を残せる。
社内が答えると税理士側に表示される。今はメール・チャットで別管理になっており、
「どの取引の話だったか」を探し直す手間が発生している。

- 明細1件に紐づくやり取りとして残る
- 解決したら閉じる。未解決の件数を月次の進捗に出す
- **MFには無い**

### 6.3 月次の進捗（税理士側のダッシュボード） 【推奨度: 中】

対象月について、残りの作業が一目で分かる。

- 未仕訳の明細: ◯件
- 証憑が未添付の仕訳: ◯件（6.1の「不要」印を除く）
- 未解決の質問: ◯件
- 共有ファイルのうち未確認: ◯件

MFにも似た画面はあるが、**共有ファイルと質問メモを含めた「この会社の月次が終わったか」**は
ここでしか出せない。

### 6.4 過去の処理を見る 【推奨度: 中】

Phase 4の提案（前回と同じ科目）の**根拠を1クリックで確認**できるようにする。
「過去5件中3件」の中身を見て、税理士が判断できる。

### 6.5 作らない方がよいと考えるもの

| 案 | 作らない理由 |
|---|---|
| 試算表・推移表の表示 | MFの方が高機能。劣化コピーになる |
| 仕訳の一括編集 | 事故が大きい。MFの画面にある |
| 決算整理仕訳の作成支援 | 会計判断そのもの。システムが関与すべきでない |
| 摘要の自動書き換え | APIに無い。かつ元データを変えるのは危険 |
| 勘定科目の自動確定（人の確認なし） | 一貫して禁止している（`TAX_WORKSPACE_PLAN.md` §9-1） |

## 7. 実装の順序（案）

| 順 | 内容 | 前提 |
|---|---|---|
| 1 | §1 共有ファイルの区分（証憑／参考資料） | 無し。すぐできる |
| 2 | §5 できないことを手順書へ明記 | 無し。すぐできる |
| 3 | §3 登録済み仕訳への証憑の紐付け（⑥タブ） | 既存の照合ロジックを流用 |
| 4 | §6.1 証憑が付いていない仕訳の一覧 | §3と同時が効率的 |
| 5 | §2 タグの追加 | 小さい |
| 6 | §6.2 質問メモ | 新規テーブルが要る |
| 7 | §4 現金払いのOCR→手動仕訳 | **P5-A・P5-Bの実測が前提** |
| 8 | §6.3 月次の進捗 | 上記が揃ってから |

⚠ **7（現金払い）を先にやらない。** 消費税の扱いが未確認のまま帳簿を触ることになる。

## 8. 実装してはいけないことリスト（Phase 5）

1. 共有ファイルの既存分を一括で「証憑」区分にする（給与明細まで添付候補に出る）
2. 拡張子だけで証憑かどうかを判断し続ける
3. `PUT /journals/{id}` で部分訂正のつもりの全体置き換えを行う
4. 現金払いの仕訳で**消費税額をアプリ側で計算する**
5. 現金払いで複合仕訳（借方または貸方が複数）を作れるようにする
6. OCRの結果を確認なしで登録に使う。想定外の形で返ったときに「それらしい値」を作る
7. 証憑の添付を自動で行う（必ず人が選ぶ）
8. 「対象外」にする機能を、APIが無いのに別の手段で再現しようとする
9. 一括登録・一括添付を作る
10. P5-A・P5-Bを実測せずに現金払いの機能を実装する
