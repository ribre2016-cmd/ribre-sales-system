# MF仕訳自動作成 UI仕様（画面モックの読み解き方）

作成: 2026-08-02 / 対応モック: `mockups/mf-journal-mock.html`
状態: **設計のみ。実装は未着手**。本書は `docs/MF_JOURNAL_PLAN.md`（以下「計画書」）の内容を
画面要素に対応づけたものであり、計画書にない意思決定は行っていない。
不明点はすべて「計画外（要検討）」と明記する。

計画書との関係: 本書と `mockups/mf-journal-mock.html` は計画書の**内容を変えない**。
条文の言い換えが計画書本文と食い違う場合は計画書が正。

| 要素 | 内容 | 計画書対応 |

| 固定警告バナー | 「これはモック（画面案）です。実データ・実APIには一切接続していません。」 | モックの位置づけそのもの（本タスクの前提） |

これは計画書に明記された事実ではなく実装者への提案＝**計画外（要検討）**。

### 1.1 勘定科目マッピングテーブル

| 税区分プルダウン | `GET /taxes` | §5.1 同上 |
| cash行の「買取先コード」 | `GET /trade_partners` | §5.1 同上／§4-B「trade_partner_codeに買取先コード」 |
| 「税理士確認後に設定」という選択済み表示 | — | §4冒頭「★全項目が税理士承認待ち」。マッピングは経営判断であり本UIが値を決めてはいけない |
| cash行に付けた黄チップ「どれになるか未定」 | — | §4-B(e)「貸方が現金/普通預金/未払金のどれかは買取の実態次第」 |
| 「最終更新: —（未設定）」 | `mf_journal_settings.updated_at` 等の想定列 | 具体的な列名は計画書に記載なし＝**計画外（要検討）**。監査のため更新者・日時の記録自体は必要（§6-10の実行者制限・実行履歴と同じ思想） |

`mf_journal_settings` は `app_settings` を使わない（`(user_email, skey)` 一意でユーザー単位のため）。
service roleのみアクセスとする（§5.1）。**実装時、この設定の読み書きAPIをどのユーザー権限で
公開するか（誰が編集できるか）は計画書に明記がなく計画外（要検討）**。

| 画面要素 | 計画書対応 |
|---|---|

## 3. ③実行履歴タブ

| 画面要素 | 計画書対応 |
|---|---|
| テーブル全体 | §6-10「実行者制限（MF_ADMIN_EMAILS）と実行履歴」 |
| createdの行 | §5.2フロー「2xx → status='created'、journal_id記録」 |
| failedの行・「明示的に再試行」ボタン（モックでは無効） | §5.2「4xx → status='failed'」／「failed=明示再試行時のみ」再試行 |
| uncertainの行・「MF側を確認」ボタン | §5.2「タイムアウト/5xx → status='uncertain'。★作成されたか不明。再試行すると二重計上になるため自動復帰させない」／「uncertainからの自動復帰禁止」(§6-9) |
| uncertain説明文（memo突合で真偽確定） | §5.2「memoに`[ribre] key=<source_key> rows=35`を埋め込み、uncertain時は当月の仕訳を全件GETしてmemoを突合」 |
| **staleの行** | ⚠️ **計画外（要検討）**。計画書§5.2で定義されるstatusは `claimed`/`created`/`failed`/`uncertain`（＋§8の`deleted`）のみで、`stale`という名称は登場しない。本モックでは「プレビュー取得後にデータが変化し409で拒否された」ケースの表示ラベルとして提案しているが、実装時にDBのstatus列へ追加するのか、それとも履歴に記録すらしない一時エラーとして扱うのかは計画書に規定がなく**要検討** |
| **unmappedの行** | ⚠️ **計画外（要検討）**。同様に計画書のstatus一覧に無い。「補助科目未設定で作成前にスキップ」はプレビュー段階の状態（②タブの「設定不足」カード）であり、これを実行履歴に1行として残すかどうかは計画書に規定なし。残すなら何がトリガーで記録されるか（ユーザーが確定を試みた時のみか、プレビュー時点で自動記録するか）も未定義 |

貫く「それらしい値を自動計算で補完しない」原則（CLAUDE.md 制約#13）と同一線上にある。

## 5. 実装してはいけないことリスト

以下はすべて計画書§6・§7・§9からの直接の禁止事項。実装フェーズでこれらを一つでも
省略・迂回した場合はリリースしない（§6冒頭「実装しないならリリースしない」）。

1. **既定ONにしない**。`enabled`は必ずfalse始まり（§6-1）
2. **プレビュー無しでの仕訳作成を許可しない**。confirm_tokenの検証を必ず挟む（§6-2）
3. **`source_key`にUNIQUE制約を付けずに運用しない**（§6-3）
4. **事前スキャンを飛ばさない**（§6-4）
5. **月ロックをクライアント側だけでチェックしない**。サーバー側で締め済み月への書き込みを拒否する（§6-5）
6. **`write_min_date`より前の月に書き込む経路を作らない**（§6-6）
7. **貸借チェックを送信前に行わない実装をしない**（§6-7）
8. **作成後の検算（GETし直して税込合計を確認）を省略しない**（§6-8。§3の1円ズレ問題の検出網）
9. **uncertainステータスから自動的に再試行・復帰させない**（§6-9・§5.2）
10. **`MF_ADMIN_EMAILS`以外のユーザーに実行権限を与えない**、実行履歴を残さない実装にしない（§6-10）
11. **Cronで起動しない**。必ず人間のクリックを起点にする（§6-11・§7「Cron禁止」相当）
12. **1回のcommitで50件を超える送信をしない**（§6-12・§5.4）
13. **`journal_type='adjusting_entry'`（決算整理仕訳）を自動生成しない**（§7）
14. **期末棚卸・売掛金の入金消込・訂正／修正仕訳・期跨ぎ／前期修正を自動化しない**（§7）
15. **現金レシートを対象にしない**（MFクラウド経費アプリの守備範囲。§7・CLAUDE.md運用の役割分担）
16. **外貨建て取引を対象にしない**（§7）
17. **Boxメタデータの入力を自動化しようとしない**（APIで書けないため。§7）
18. **`sales`/`purchases`テーブルに`journal_id`列を追加しない**。`mf_journal_links`をsource_keyで結合する唯一の正とする（§5.3）
19. **勘定科目・税区分・invoice_kindをコード側で推測・自動決定しない**（§4-C「絶対にしない」・§10-4「invoice_kindはコード側で推測してはならない」）
20. **一般的な「削除」ボタンを公開しない**。Undoは24時間以内・同一ユーザー・税理士未編集・証憑未添付・未締め月の4条件を全て満たす場合のみ（§8）
21. **A1〜A3が未解決のまま実データに仕訳を作成しない**（§11・§3）

## 6. 実装開始の前提条件

以下がすべて揃うまで、Phase 2（EC売上の月次集計仕訳の自動作成）の実装に着手しない。

1. **§10 税理士・オーナー確認14項目の回答が揃っていること**（§10冒頭「回答が揃うまでPhase 2に進まない」）
2. **§11 A1〜A3（消費税額の明示指定可否／tax_valueの算出方法／貸借不一致時のAPI挙動）の実測が完了していること**（§11「特にA1〜A3が解決するまで、実データに対する仕訳作成は絶対に実行しないこと」、§3「テスト仕訳を1件だけ作成→即GET→即削除して実測する（Phase 0）」）
3. **`journal.write`スコープの再認可が完了していること**（§2「既存トークンにはjournal.writeが無い。ユーザーの再認可が必須」／MF開発者ポータル側のスコープ追加も含む）

上記3点はいずれも計画書に明記された前提であり、順序や優先度についての計画書の言及はない。
Phase 0（スコープ追加・再認可・実測）と税理士確認14項目は並行して進められる別トラックだが、
**両方が揃わない限りPhase 2のコードを書き始めない**というのが計画書の一貫した方針である。
